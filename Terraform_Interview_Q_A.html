🗄️ State & Locking Issues
Q01
State · Production Incident
Your CI/CD pipeline runs terraform apply and gets: "Error acquiring the state lock. Lock Info: ID: xxx" — but no one is currently running Terraform. How do you resolve this in production?
🔥 Hot Topic State Lock
Answer
This happens when a previous Terraform run was killed mid-flight (pipeline timeout, OOM, manual Ctrl+C) and did not release the lock. The lock record stays in the backend.
  • 1Identify the stale lock ID from the error message — it shows the Lock ID, Who, and When it was acquired.
  • 2Verify no active apply is running: check your CI/CD platform for any active jobs.
  • 3For Azure backend: the lock is a blob lease on the state file in Storage Account. You can break the lease via Azure Portal → Storage → Blob → Break Lease, OR use the Terraform command.
  • 4Run force-unlock with the Lock ID shown in the error.
# Force unlock using the Lock ID from the error output terraform force-unlock LOCK_ID_FROM_ERROR # For Azure: you can also break the blob lease directly az storage blob lease break \ --blob-name prod.terraform.tfstate \ --container-name tfstate \ --account-name sttfstate001
Pro tip: In Azure DevOps pipelines, always set a cancel job step to run terraform force-unlock if the pipeline is cancelled. Never use -lock=false in production — it bypasses protection entirely.
force-unlock Azure blob lease Never -lock=false in prod
Q02
State · Corruption
Your production state file got corrupted — terraform plan throws a JSON parse error. The application is still running. How do you recover without destroying infra?
🔥 CriticalState Recovery
Answer
State file corruption is one of the most stressful production incidents. The recovery approach depends on whether you have versioned backups — which is why enabling versioning on your Azure Storage Account is non-negotiable.
  • 1Do NOT run terraform apply. First, pull a copy of the corrupted state for analysis: terraform state pull > corrupted.tfstate
  • 2Check Azure Storage versioning — go to the blob in Azure Portal, click "View versions" and restore the last known good version.
  • 3If no versioning, use terraform import to rebuild state resource by resource from existing Azure infrastructure.
  • 4After restoring, run terraform plan — it should show only minor diffs, not mass destruction.
  • 5Going forward: enable blob versioning, implement daily state backups, use terraform state pull snapshots in CI.
# Pull current (corrupted) state terraform state pull > backup_corrupted.tfstate # Restore previous version (Azure CLI) az storage blob copy start \ --source-container tfstate \ --source-blob "prod.tfstate?versionid=2024-01-01T10:00:00.000Z" \ --destination-container tfstate \ --destination-blob prod.terraform.tfstate # Verify plan looks sane after restore terraform plan
Prevention: Always configure Azure Storage with versioning_enabled = true and blob_soft_delete_enabled = true via Terraform itself.
Q03
State · Concurrent Apply
Two developers push to main branch simultaneously. Both pipelines trigger terraform apply at the same time against the same state backend. What happens and how do you prevent it?
⚠️ MediumConcurrency
Answer
What happens: The first pipeline acquires the state lock. The second pipeline will block and wait (up to the lock timeout), then fail with "Error acquiring the state lock" — which is the correct behaviour. However, if both somehow apply, you risk state corruption and resource inconsistency.
Correct solution: Prevent two applies from ever running simultaneously using pipeline-level concurrency controls.
# Azure DevOps — use pipeline resource locking # In azure-pipelines.yml: lockBehavior: sequential # queue applies instead of parallel # GitHub Actions — use concurrency groups concurrency: group: terraform-prod cancel-in-progress: false # queue, don't cancel # Azure backend also provides blob-level locking automatically terraform { backend "azurerm" { resource_group_name = "rg-tfstate" storage_account_name = "sttfstate001" container_name = "tfstate" key = "prod.tfstate" # Azure blob leases provide automatic state locking } }
pipeline concurrency blob lease locking sequential queue
📡 Infrastructure Drift Scenarios
Q04
Drift · Emergency Fix
A junior engineer manually opened port 22 on a production NSG in the Azure Portal during an incident (bypassing Terraform). The next CI pipeline terraform apply will revert that change automatically. How do you handle this?
🔥 Real WorldDrift
Answer
This is a classic infrastructure drift scenario. You have two choices depending on whether the manual change should be permanent or temporary.
  • 1Run terraform plan immediately — it will show the drift (port 22 rule as "to be deleted"). This confirms what Terraform sees.
  • 2If the rule must stay: Update the Terraform code to include the port 22 rule. This makes it permanent and code-tracked. Commit and push.
  • 3If temporary (incident only): Add ignore_changes for NSG rules until the incident is resolved, then remove it and revert via Terraform.
  • 4Long-term fix: Lock the NSG resource in Azure Portal so manual edits are blocked. Enforce IaC-only changes via Azure Policy.
# Option A: Add the change to Terraform code (recommended) resource "azurerm_network_security_rule" "allow_ssh_temp" { name = "allow-ssh-incident" priority = 150 direction = "Inbound" access = "Allow" protocol = "Tcp" destination_port_range = "22" source_address_prefix = "10.0.0.0/8" # restrict to internal network_security_group_name = var.nsg_name resource_group_name = var.rg_name } # Option B: Temporarily ignore changes on NSG resource "azurerm_network_security_group" "nsg" { lifecycle { ignore_changes = [security_rule] # TEMPORARY — remove after incident } }
Best practice: Set up drift detection as a scheduled pipeline job that runs terraform plan daily and alerts on any unexpected diffs. Treat drift as an incident.
Q05
Drift · Detection
How would you set up automated drift detection in production so you know when someone makes manual changes in the Azure Portal?
⚠️ MediumDrift Detection
Answer
Drift detection is a scheduled pipeline that runs terraform plan in read-only mode without applying changes. Any non-empty plan output means drift has occurred.
# Azure DevOps — scheduled drift detection pipeline (YAML) schedules: - cron: "0 7 * * *" # Every day at 7 AM IST displayName: Drift Detection branches: include: [main] always: true steps: - script: terraform init - script: | terraform plan -detailed-exitcode -out drift.tfplan 2>&1 exit_code=$? if [ $exit_code -eq 2 ]; then echo "##vso[task.logissue type=error]DRIFT DETECTED!" exit 1 # fail pipeline → triggers alert fi displayName: Detect Drift # -detailed-exitcode: 0=no diff, 1=error, 2=diff found # Pair with Azure Monitor alert on pipeline failure → Teams/Slack notification
-detailed-exitcode scheduled pipeline Teams/Slack alert
💣 Accidental Destroy & Protection
Q06
Destroy · Production Database
A developer renamed a Terraform resource block for a production Azure SQL database. The next terraform plan shows the old DB will be DESTROYED and a new one created. How do you prevent data loss?
🔥 Criticalprevent_destroy
Answer
This is caused by the resource address changing — Terraform treats a rename as destroy-and-create. You need to update the state reference, not recreate the resource. Two complementary solutions:
  • 1Immediate fix: Use terraform state mv to rename the state reference to match the new name. No infra is touched.
  • 2Or use a moved block (TF 1.1+) — declarative, reviewable in PR, cleaner.
  • 3Prevention: Add prevent_destroy = true in the lifecycle block of all production databases.
  • 4CI gate: Add a policy check in your pipeline that fails if the plan contains any resource destruction of critical resource types.
# Fix 1: state mv — no infra change, just state rename terraform state mv \ azurerm_mssql_database.old_name \ azurerm_mssql_database.new_name # Fix 2: moved block in your .tf code (preferred) moved { from = azurerm_mssql_database.old_name to = azurerm_mssql_database.new_name } # Prevention: lifecycle guard on all prod databases resource "azurerm_mssql_database" "prod_db" { name = "sqldb-prod" server_id = var.sql_server_id lifecycle { prevent_destroy = true } }
CI gate script: Run terraform show -json drift.tfplan | jq '[.resource_changes[] | select(.change.actions[] == "delete")]' and fail the pipeline if any critical resources appear in the destroy list.
Q07
Destroy · Runaway
Someone accidentally ran terraform destroy on a production environment and it deleted 30+ resources before you stopped it. How do you recover?
🔥 Nightmare ScenarioDisaster Recovery
Answer
This is a major incident. First: stay calm and stop further destruction. Then follow this recovery playbook:
  • 1Stop the destroy — Ctrl+C immediately if still running. Check state to see what remains.
  • 2Check Azure soft-delete / snapshots — Many Azure resources (VMs, Storage, Key Vault, SQL) have soft-delete or point-in-time restore. Use Azure Portal to recover them first.
  • 3Restore state — Pull the last good state from Azure Storage blob version history. Without state, Terraform won't know these resources existed.
  • 4Import recovered resources — For any resources you restored manually, use terraform import to re-link them to the state.
  • 5Run terraform apply (not destroy) — with the restored state, Terraform will recreate any still-missing resources.
  • 6Post-incident: Add prevent_destroy, restrict who can run terraform destroy, require manual approval in pipelines.
# Restore state from Azure blob versioning az storage blob list-versions \ --container-name tfstate \ --name prod.terraform.tfstate \ --account-name sttfstate001 # Recover a soft-deleted Azure Key Vault az keyvault recover --name kv-prod-001 # Import a recovered resource back into state terraform import azurerm_resource_group.main \ /subscriptions/<id>/resourceGroups/rg-prod
Prevention: In Azure DevOps, create a separate pipeline for destroy that requires 2 approvals from team leads. Never run terraform destroy from a developer's local machine on prod.
🔄 Refactoring Without Downtime
Q08
Refactor · count → for_each
You have 5 Azure VMs created with count. You need to migrate to for_each without recreating any VMs. What is your approach?
🔥 Common TrapRefactor
Answer
Changing from count to for_each changes the resource address in state (from vm[0] to vm["name"]), which Terraform reads as destroy-and-recreate. You must use terraform state mv or moved blocks to map old addresses to new ones.
# OLD code (count-based) — addresses are vm[0], vm[1]... resource "azurerm_linux_virtual_machine" "vm" { count = length(var.vm_names) name = var.vm_names[count.index] } # NEW code (for_each-based) resource "azurerm_linux_virtual_machine" "vm" { for_each = toset(var.vm_names) name = each.key } # MIGRATION: Add moved blocks (one per VM) moved { from = azurerm_linux_virtual_machine.vm[0] to = azurerm_linux_virtual_machine.vm["vm-app-01"] } moved { from = azurerm_linux_virtual_machine.vm[1] to = azurerm_linux_virtual_machine.vm["vm-app-02"] } # terraform plan → should show "moved" not "destroyed"
Always run plan first after adding moved blocks. If the plan shows zero destroy actions and only move operations, you are safe to apply.
Q09
Refactor · Module Extraction
You want to extract inline resources into a reusable module without destroying and recreating the existing Azure infrastructure. How do you safely do this?
⚠️ MediumModules
Answer
When you move a resource into a module, the state address changes from azurerm_virtual_network.vnet to module.network.azurerm_virtual_network.vnet. Terraform sees this as a new resource. Use a moved block to tell it the addresses are the same physical resource.
# Before: inline resource resource "azurerm_virtual_network" "vnet" { ... } # After: in a module module "network" { source = "./modules/network" name = "vnet-prod" } # Bridge: moved block in root moved { from = azurerm_virtual_network.vnet to = module.network.azurerm_virtual_network.this } # Result: terraform plan shows "moved" — zero recreation
moved block zero downtime state address change
🔐 Secrets & Security
Q10
Secrets · Leak
A developer committed a terraform.tfvars file containing database passwords to Git. The secret is now in history. What are your immediate steps and long-term fixes?
🔥 Security IncidentSecrets
Answer
This is a security incident. Treat the secret as compromised the moment it was committed — even if the repo is private.
  • 1Immediately rotate the secret — change the DB password in Azure right now. The old one is compromised.
  • 2Remove from Git history using git filter-branch or BFG Repo Cleaner. Force-push all branches.
  • 3Revoke and audit — check Azure AD sign-in logs for any unexpected DB access using the leaked credential.
  • 4Long-term fix: Store all secrets in Azure Key Vault. Terraform should fetch them at runtime via data source — never store values in tfvars.
  • 5Add *.tfvars to .gitignore. Add pre-commit hooks with tools like git-secrets or detect-secrets.
# WRONG: password in tfvars (never do this) db_password = "SuperSecret123!" # RIGHT: Fetch from Azure Key Vault at runtime data "azurerm_key_vault_secret" "db_pass" { name = "db-admin-password" key_vault_id = var.key_vault_id } resource "azurerm_mssql_server" "sql" { administrator_login_password = data.azurerm_key_vault_secret.db_pass.value }
Best practice: Use Managed Identity where possible so there's no password at all. Azure services authenticate to each other without credentials.
Q11
Secrets · State File
You realize your Terraform state file contains plain-text database passwords (from a random_password resource). The state file is stored in Azure Storage. What do you do?
⚠️ MediumSecrets
Answer
Terraform state files always contain sensitive values in plain text — this is a known limitation. The state file cannot be encrypted by Terraform itself, so you must secure the storage layer.
  • 1Enable Storage Account encryption — Azure Storage encrypts at rest by default with Microsoft-managed keys. For higher security, use Customer-Managed Keys (CMK) in Key Vault.
  • 2Restrict access — Use Azure RBAC to limit who can read the blob. Only the Terraform service principal and pipeline identity should have access.
  • 3Enable Private Endpoint on the Storage Account so it's not accessible from the public internet.
  • 4Mark variables sensitive — Although this doesn't encrypt state, it prevents values from appearing in plan/apply output.
# Secure state storage in Azure resource "azurerm_storage_account" "tfstate" { name = "sttfstate001" resource_group_name = var.rg_name location = var.location account_tier = "Standard" account_replication_type = "GRS" min_tls_version = "TLS1_2" allow_nested_items_to_be_public = false blob_properties { versioning_enabled = true delete_retention_policy { days = 30 } } } # + Add azurerm_private_endpoint for network isolation
⚙️ CI/CD Pipeline Issues
Q12
CI/CD · Plan vs Apply Mismatch
Your pipeline runs terraform plan and it shows no changes. But when terraform apply runs 10 minutes later in the same pipeline, it suddenly wants to destroy resources. Why does this happen and how do you prevent it?
🔥 TrickyCI/CD
Answer
This happens because another apply ran between your plan and apply, or the real infrastructure changed in that window. The plan was calculated against a different state than what apply sees.
Fix: Always save the plan to a file and apply that exact saved plan — not a fresh plan.
# WRONG: plan and apply separately — state can change between them terraform plan terraform apply # runs a fresh plan internally! # RIGHT: save plan, apply the exact saved artifact terraform plan -out=tfplan.binary # save plan to file # Upload tfplan.binary as pipeline artifact # Download in apply stage: terraform apply tfplan.binary # applies EXACTLY what was planned # Azure DevOps pipeline stages: # Stage 1 (Plan): terraform plan -out=tfplan.binary # Stage 2 (Approval gate) # Stage 3 (Apply): terraform apply tfplan.binary
Always separate Plan and Apply into different pipeline stages with the plan output saved as an artifact. This ensures the apply executes exactly what was reviewed and approved.
Q13
CI/CD · Provider Auth
Your Terraform pipeline in Azure DevOps authenticates using a Service Principal client secret, but the secret expires every 90 days causing pipeline failures. How do you fix this long-term?
⚠️ OperationalAuthentication
Answer
The best long-term solution is to eliminate the secret entirely using OIDC (Workload Identity Federation) for GitHub Actions or Managed Identity for Azure DevOps-hosted agents.
# Option 1: Managed Identity (Azure DevOps self-hosted agent) # Assign contributor role to the agent's managed identity # In provider — no credentials needed: provider "azurerm" { features {} use_msi = true # authenticate via Managed Identity subscription_id = var.subscription_id } # Option 2: OIDC federation (GitHub Actions — no secret at all) # GitHub Actions YAML: permissions: id-token: write contents: read - uses: azure/login@v1 with: client-id: ${{ secrets.AZURE_CLIENT_ID }} tenant-id: ${{ secrets.AZURE_TENANT_ID }} subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }} # No client-secret! Uses OIDC token exchange
Managed Identity = zero secrets to rotate. For Azure DevOps with Microsoft-hosted agents, use OIDC + Workload Identity Federation. This is the recommended approach for 2024+.
Q14
CI/CD · Partial Apply
A terraform apply runs in your pipeline and fails halfway through — 12 of 25 resources were created, 13 failed. The pipeline is now showing an error. What do you do?
🔥 IncidentPartial Apply
Answer
Terraform is designed to be idempotent — the correct response to a partial apply is simply to run apply again. Terraform will skip the 12 already-created resources and attempt only the 13 that failed.
  • 1Read the error message carefully. Understand WHY the apply failed (quota limit, permission denied, dependency issue, etc.).
  • 2Fix the root cause — request quota increase, fix RBAC, fix the dependency order, or use depends_on.
  • 3Run terraform apply again — Terraform reads the current state, sees 12 resources already exist, and only creates the remaining 13.
  • 4Do NOT run terraform destroy first — that would tear down the 12 that were successfully created.
# Check current state to see what was created terraform state list # Show details of a specific resource terraform state show azurerm_subnet.web # Fix the issue, then simply re-run apply terraform apply # idempotent — only creates what's missing
📦 Module & Multi-Environment Issues
Q15
Modules · Version Breaking Change
You updated a shared Terraform module from v1.2 to v2.0 (breaking change). How do you roll this out across 10 teams using the module without breaking everyone's production?
🔥 EnterpriseModules
Answer
The key is that all teams pin to a specific module version. A breaking change in v2.0 does not automatically affect anyone using version = "~> 1.2".
  • 1Publish v2.0 with a CHANGELOG documenting breaking changes and migration guide.
  • 2Teams opt-in explicitly — they update their source version pin and test in dev/staging first.
  • 3Maintain v1.x with security patches for a deprecation window (e.g., 3 months) to give teams time to migrate.
  • 4Canary rollout — pilot team upgrades first, validates in prod, then others follow.
# Teams pin module versions — v2.0 won't auto-affect them module "network" { source = "git::https://github.com/org/tf-modules.git//network" version = "~> 1.2" # safe: won't pick up v2.0 } # Team upgrades explicitly: module "network" { source = "git::https://github.com/org/tf-modules.git//network" version = "~> 2.0" # opt-in to v2 after testing }
Best practice: Use Git tags for versioning (v1.2.0, v2.0.0) and host modules in a private Terraform Registry or Azure Artifacts feed for version discoverability.
Q16
Modules · Large State
Your Terraform state file has grown to 50MB with 800+ resources. terraform plan takes 20+ minutes. How do you fix this?
⚠️ PerformanceState
Answer
A monolithic state is an anti-pattern at scale. The solution is to split the state into logical stacks (networking, compute, data, apps) — each with its own state file.
  • 1Identify logical boundaries: networking/, compute/, databases/, apps/
  • 2Use terraform state mv to move resources into the new state files one group at a time.
  • 3Use terraform_remote_state data sources for cross-stack references (e.g., compute stack reads VNet ID from network stack output).
  • 4Intermediate fix: use -target flag to run plan on a subset of resources only during migration.
# Move resources to new state file terraform state mv \ -state=monolith.tfstate \ -state-out=network.tfstate \ azurerm_virtual_network.vnet # Cross-stack reference in compute stack data "terraform_remote_state" "network" { backend = "azurerm" config = { resource_group_name = "rg-tfstate" storage_account_name = "sttfstate001" container_name = "tfstate" key = "network/eastus.tfstate" } } # Now plan only touches 80 compute resources instead of 800

Provider · API Rate Limiting
Your terraform apply intermittently fails with "429 Too Many Requests" from Azure's REST API, especially when creating 50+ resources. How do you handle this?
⚠️ MediumProvider
Answer
Azure ARM API has per-subscription rate limits. The azurerm provider and Terraform have mechanisms to handle this gracefully.

-parallelism=5 time_sleep resource -target batching
Q18
Provider · Version Upgrade
After upgrading the AzureRM provider from 3.x to 4.x, your terraform plan shows unexpected changes across 200 resources even though you changed nothing in your code. What happened?
🔥 TrapProvider
Answer
Major provider version bumps (3.x → 4.x) often have breaking changes, renamed attributes, or new defaults. The provider is now interpreting your unchanged HCL differently, producing a diff against the real infrastructure.
  • 1Read the provider changelog at registry.terraform.io/providers/hashicorp/azurerm — look for breaking changes in the upgrade guide.
  • 2Rollback immediately in the .terraform.lock.hcl by reverting the provider version pin.
  • 3Test the upgrade in dev first — review every resource change in the plan output, then update your code to match new attribute names.
  • 4Always pin provider versions using ~> to allow only minor/patch updates, not major version jumps.
# Always pin versions — prevent surprise upgrades terraform { required_providers { azurerm = { source = "hashicorp/azurerm" version = "~> 3.80" # locks to 3.x only, never 4.x } } required_version = ">= 1.5.0, < 2.0.0" } # .terraform.lock.hcl is committed to Git # This ensures ALL team members and pipelines use identical provider versions # terraform init -upgrade # to update lock file deliberately
Always commit .terraform.lock.hcl to Git. This is the provider equivalent of package-lock.json — it guarantees reproducible runs across all machines and pipelines.
Q19
Performance · Circular Dependency
Terraform fails with: "Error: Cycle: resource A depends on resource B, resource B depends on resource A". How do you identify and resolve circular dependencies in production?
⚠️ MediumDependencies
Answer
Circular dependencies usually happen when two resources both reference each other's attributes. The fix is to break the cycle by introducing an intermediate resource or using -target for bootstrap ordering.
# Identify the cycle visually terraform graph | dot -Tsvg > dependency_graph.svg # Common scenario: NSG ↔ Subnet association cycle # PROBLEM: subnet references NSG, NSG references subnet # SOLUTION: Decouple using a separate association resource resource "azurerm_subnet" "web" { name = "snet-web" virtual_network_name = var.vnet_name resource_group_name = var.rg_name address_prefixes = ["10.0.1.0/24"] # Don't set network_security_group_id here } resource "azurerm_network_security_group" "nsg" { name = "nsg-web" resource_group_name = var.rg_name location = var.location } # Association resource AFTER both — breaks the cycle resource "azurerm_subnet_network_security_group_association" "assoc" { subnet_id = azurerm_subnet.web.id network_security_group_id = azurerm_network_security_group.nsg.id }
🎯 Advanced Production Scenarios
Q20
Terraform · Import at Scale
You've inherited 200+ Azure resources created manually by a previous team. Management wants everything under Terraform control. What is your import strategy?
🔥 EnterpriseImport
Answer
Importing 200 resources manually is impractical. Use a phased approach with automation.
  • 1Audit everything first — use Azure Resource Graph to list all resources with their IDs.
  • 2Use aztfexport (AzAPI) — Microsoft's official tool that generates both Terraform config AND import blocks from existing Azure resources automatically.
  • 3Prioritize by risk — import networking first (most shared), then compute, then apps.
  • 4After each import, run terraform plan — it should show NO changes. If it shows changes, fix your HCL to match the real resource before proceeding.
  • 5Freeze changes on those resources until they're fully under Terraform control.
# Use aztfexport for bulk generation aztfexport resource-group --resource-group-name rg-prod # Or use TF 1.5+ import blocks in bulk import { to = azurerm_virtual_network.vnet id = "/subscriptions/xxx/resourceGroups/rg-prod/providers/Microsoft.Network/virtualNetworks/vnet-prod" } # Generate config from import blocks: terraform plan -generate-config-out=generated.tf # Review generated.tf → clean it up → terraform apply
Terraform 1.5+ generate-config-out can auto-generate HCL from import blocks. This dramatically speeds up large-scale imports.
Q21
Multi-Env · Environment Promotion
How do you implement a prod-identical staging environment and ensure changes are validated there before being promoted to production?
⚠️ DesignEnvironments
Answer
Use the same Terraform modules for both environments, with different tfvars files controlling the differences (VM size, replica counts, etc.). The key is one code path, different variable inputs.
# Directory structure # environments/ # staging/ → terraform.tfvars (smaller SKUs, 1 replica) # prod/ → terraform.tfvars (larger SKUs, 3 replicas) # staging.tfvars vm_size = "Standard_B2s" db_sku = "GP_Gen5_2" replica_count = 1 environment = "staging" # prod.tfvars vm_size = "Standard_D4s_v3" db_sku = "BC_Gen5_4" replica_count = 3 environment = "prod" # Pipeline: staging apply → manual approval gate → prod apply # Azure DevOps: use Environments with approval checks
Environments share the same modules but have separate state backends. Staging should use identical resource types as prod — just smaller. Using different resource types (e.g., Free tier in staging) hides compatibility bugs.
Q22
Zero Downtime · Blue-Green
You need to update a production VM SKU in Azure using Terraform. The resource requires replacement (destroy + create). How do you do this with zero downtime?
🔥 ProductionZero Downtime
Answer
Use create_before_destroy = true in the lifecycle block. This tells Terraform to spin up the new VM first, and only destroy the old one after the new one is healthy.
resource "azurerm_linux_virtual_machine" "app" { name = "vm-app-prod" size = var.vm_size # change Standard_B2s → Standard_D4s_v3 lifecycle { create_before_destroy = true } } # For stateless apps: use VMSS (scale sets) with rolling upgrade resource "azurerm_linux_virtual_machine_scale_set" "app" { upgrade_mode = "Rolling" rolling_upgrade_policy { max_batch_instance_percent = 25 max_unhealthy_instance_percent = 20 max_unhealthy_upgraded_instance_percent = 20 pause_time_between_batches = "PT5M" } } # VMSS rolling upgrade: replaces 25% at a time, 5-min pause between batches
Q23
State · Backend Migration
Your team has been using local state files. You need to migrate to Azure Storage backend without losing any state and without disrupting any running infrastructure. Walk through the steps.
⚠️ OperationalBackend Migration
Answer
Terraform has a built-in migration command. The process is safe and non-destructive — your infrastructure is not touched during backend migration.
  • 1Create the Azure Storage Account for state (using Azure CLI or portal — do this first, outside of Terraform).
  • 2Add the backend block to your terraform.tf configuration.
  • 3Run terraform init -migrate-state — Terraform detects you have local state and offers to copy it to the new remote backend.
  • 4Terraform copies the state. Run terraform plan — should show NO changes (state is identical).
  • 5Delete or archive the local terraform.tfstate file and never commit it to Git again.
# Step 1: Create storage outside Terraform (one-time) az storage account create -n sttfstate001 -g rg-tfstate --sku Standard_LRS az storage container create -n tfstate --account-name sttfstate001 # Step 2: Add backend to main.tf terraform { backend "azurerm" { resource_group_name = "rg-tfstate" storage_account_name = "sttfstate001" container_name = "tfstate" key = "prod.terraform.tfstate" } } # Step 3: Migrate terraform init -migrate-state # copies local state → Azure blob # Step 4: Verify terraform plan # must show zero changes
Q24
Policy · Compliance Gate
Your security team requires that all Azure resources in production must have specific tags (CostCenter, Owner, Environment) and no public IPs should be created. How do you enforce this in your Terraform pipeline?
⚠️ CompliancePolicy
Answer
Multi-layer enforcement: Terraform validation + static analysis in CI + Azure Policy as a backstop.
# Layer 1: Terraform variable validation variable "tags" { type = object({ CostCenter = string, Owner = string, Environment = string }) validation { condition = contains(["dev","staging","prod"], var.tags.Environment) error_message = "Environment must be dev, staging, or prod." } } # Layer 2: checkov scan in CI (catches public IPs, missing tags) # In azure-pipelines.yml: # - script: pip install checkov && checkov -d . --framework terraform # Layer 3: Azure Policy (enforced even outside Terraform) resource "azurerm_policy_assignment" "require_tags" { name = "require-tags" scope = var.subscription_id policy_definition_id = "/providers/Microsoft.Authorization/policyDefinitions/..." parameters = jsonencode({ tagName = { value = "CostCenter" } }) }

Terraform · Multi-Subscription
You need to deploy resources across 3 Azure subscriptions (hub, spoke-dev, spoke-prod) in a single Terraform run. How do you configure this and what challenges arise?
🔥 EnterpriseMulti-Sub
Answer
Use provider aliases — one azurerm provider block per subscription with an alias. Resources specify which provider (subscription) they belong to.
# providers.tf — one alias per subscription provider "azurerm" { features {} alias = "hub" subscription_id = var.hub_subscription_id } provider "azurerm" { features {} alias = "spoke_dev" subscription_id = var.dev_subscription_id } provider "azurerm" { features {} alias = "spoke_prod" subscription_id = var.prod_subscription_id } # Use alias in resources resource "azurerm_virtual_network" "hub_vnet" { provider = azurerm.hub name = "vnet-hub" ... } resource "azurerm_virtual_network_peering" "hub_to_dev" { provider = azurerm.hub remote_virtual_network_id = azurerm_virtual_network.dev_vnet.id ... } # Challenge: Service Principal must have Contributor # access across all 3 subscriptions, OR use separate SPs # with assume_identity per provider alias.
Enterprise recommendation: Use a dedicated "Terraform SP" with RBAC contributor on all three subscriptions, and store cross-subscription state keys in a shared backend using separate blob keys per environment.
